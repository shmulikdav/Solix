Writing a `solix gate` policy used to take trial runs. This release lets you check a policy before an agent ever runs under it, start a policy from the defaults, and stop worrying about `2>&1`. It also closes a gap that let a hand-written regex rule cover files outside the project.

**1,317 tests. 46 claims in `docs/CLAIMS.md`, each with a test that fails when it stops being true.**

## What prompted it

On 2026-11-03 a hand-written policy for a gated `npm publish --dry-run` was refused three times before the dry run ever ran: first for a missing `head`, then for a `2>&1` the policy's regex didn't expect. The gate was right each time. But the only way to find out what a policy would do was to run a real agent under it and read the refusal.

## `solix rules test`

```sh
solix rules test --rules .solix/policy.json "npm view @shmulikdav/solix version 2>&1; git status --short"
```

```
    ✗ npm view @shmulikdav/solix version 2>&1  no rule covers this
    ✓ git status --short                       allow shell commands starting with `git status`

  NOT COVERED. Under `solix gate` it is refused at once; at the desk it waits for a person.
```

- The verdict is the gate's own. It is computed by the same function the gate decides with, not worked out again.
- When a command is not covered, it says which part. Either *no rule covers this*, or *`cat` matches, but /etc/hostname is outside the project*.
- The denylist is reported first.
- `--rules <file|defaults>` tests a policy. Without it, the command tests the rules in force on this machine. `--file <path>` tests a file tool instead.
- Exit codes are `0` for allowed, `1` for not allowed and `2` for a policy that doesn't load, so it can sit in CI next to the gate run it predicts.

## Policies can extend the defaults

```json
{
  "extends": "defaults",
  "rules": [
    { "tool": "Bash", "match": "command_regex", "value": "^npm (pack|publish) --dry-run$" },
    { "tool": "Bash", "match": "command_prefix", "value": "git commit", "decision": "deny" }
  ]
}
```

You no longer have to list every read-only command an agent might pipe through. Deny rules still win, so a policy can start from the defaults and refuse something they allow.

## Rules match the command, not its plumbing

Redirects that only move or discard output (`2>&1`, `>&2`, `>/dev/null`) are ignored when matching. `^npm (pack|publish) --dry-run$` now covers `npm publish --dry-run 2>&1`. It still does not cover `npm publish`, `--dry-run --dry-run=false`, `… 2>&1 && npm publish` or `> out.log`.

## Security: regex allow rules were not confined

A prefix allow rule never covers a command that names a path outside the project. Regex allow rules skipped that check, so a rule like `^cat ` covered `cat ~/.ssh/id_ed25519`. Every allow rule now applies the same check.

**Who was affected:** only people who wrote their own **regex** allow rules. No default rule is a regex. The denylist ran first throughout.

## Also

- `pnpm release:tag` lists the files that make the working tree dirty, instead of only saying that it is.

## Upgrading

```sh
npm i -g @shmulikdav/solix
```

Existing rules are kept. A regex allow rule that matched a command naming a path outside the project now leaves that command to a person, or refuses it under `solix gate`, instead of allowing it.

A security fix for the approval rules. **Upgrade if you use `solix rules defaults` or `solix gate`.** This release also writes down what the gate guarantees and what it doesn't: [`docs/THREAT-MODEL.md`](https://github.com/shmulikdav/Solix/blob/main/docs/THREAT-MODEL.md).

**1,372 tests. 48 claims in `docs/CLAIMS.md`, each with a test that fails when it stops being true.**

## What was wrong

A probe of the default rules after 1.20.2 found every one of these **auto-allowed**: at the desk without asking, and under `solix gate` despite the policy.

| Command | Why it got through |
|---|---|
| `Read ~/.ssh/id_ed25519`, `Read /etc/passwd` | the read-only rule never looked at a path |
| `Grep` with `path: $HOME`, `Glob ~/.aws/*` | same |
| `cat $HOME/.ssh/id_ed25519`, `cat ${HOME}/.aws/credentials` | a path through a variable wasn't recognised |
| `cat ../../.ssh/id_ed25519`, `echo x > ../../.bashrc` | only absolute paths were checked |
| `git log --output=/etc/x`, `sort -o/etc/x` | option values weren't checked |
| `cat <(rm -rf ./src)` | process substitution was "a `cat`" |

When Solix allows a call it answers the hook itself, so Claude Code didn't ask either.

**What was never exposed:** the denylist runs before any rule and was unaffected. `rm -rf /`, writes to SSH keys, raw block devices, `curl | sh` and `sudo` were refused throughout.

## The fix

An allow rule never covers a path outside the project or the session scratchpad, however the path is spelled:

- **Variables:** `$HOME`, `${HOME}`, `$PWD` and `$TMPDIR` are expanded, and so is a variable assigned earlier in the same command. Any other variable counts as outside, because a rule can't vouch for a path it can't read.
- **`..`:** resolved from the directory the call actually runs in, so `cat ../server/x` from `packages/cli` is still inside.
- **Redirect targets and options:** `> ../x` (with or without a space), `--output=/x`, `-o/x` and `key=../x` are each checked as a path.
- **Symlinks:** followed, so a link inside the project that points out of it is outside.
- **Substitutions:** `<( … )` and `>( … )` are judged as their own commands, like `$( … )`.
- **Reads:** `Read`, `Grep` and `Glob` are allowed inside the project only. `Write` and `Edit` follow symlinks.

Claims `CLAIM-RULES-SEE-EVERY-PATH` and `CLAIM-READS-CONFINED` hold this. Removing any one of the ten checks fails its tests.

Everyday commands are still allowed, and are tested: `cat package.json | head -60`, `cd src && ls`, `echo $HOME`, `npm test 2>&1 | tail -20`, `S=src/out; mkdir -p $S`.

## What the gate does and doesn't guarantee

New: [`docs/THREAT-MODEL.md`](https://github.com/shmulikdav/Solix/blob/main/docs/THREAT-MODEL.md). In short:

- **Rules are standing decisions, not a sandbox.** Allowing `npm test` allows whatever the tests do.
- **Only some tools go through Solix's gate:** `Bash`, `Read`, `Write`, `Edit`, `MultiEdit` and `Task`.
- **Solix doesn't control the network.**
- **For hard isolation,** run the agent in a container, or use `SOLIX_SANDBOX_CMD`.

`SECURITY.md` said the gate was off by default. It is **on, fail-closed**, for every agent Solix launches, and that is now stated correctly.

## Upgrading

```sh
npm i -g @shmulikdav/solix
solix start
```

Your existing rules are kept. A command they used to allow that reaches outside the project is now asked about, or refused under `solix gate`. `solix rules test "<command>"` shows what the gate will do with any command.
